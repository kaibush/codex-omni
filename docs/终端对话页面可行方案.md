# Codex Omni 终端对话页面可行方案

## 结论

可以实现，而且应当作为一类新的工作台页面/Session 类型加入，保留现有对话页和现有“终端工具 Tab”不动。

推荐的产品形态是“终端对话 Session”：页面上方是 ANSI 终端输出区，下方沿用当前发送框的三层结构；用户可以选择 `codex`、`claude`、`gemini` 或管理员配置的其他 CLI，直接与真实 PTY 交互。终端输入、输出、命令进程和历史均属于该 Session，浏览器只是一个可随时连接或离开的客户端。

需要特别区分三种生命周期：

1. 浏览器 WebSocket 断开：只代表暂时离开，不能杀进程。
2. CLI 子进程退出：记录退出原因，由重启策略决定是否重启。
3. Server 重启：旧 PTY 随 Server 正常结束；Server 启动后根据 SQLite 中的 `desiredState` 重新启动对应 CLI，并回放已经落盘的历史输出。不承诺保留原 PID 或原 TTY 现场。

## 当前实现基线与缺口

仓库已经具备 `node-pty`、`TerminalManager`、`/api/terminal/ws`、序号回放、xterm.js、复制/粘贴、搜索、Ctrl/Alt/Shift 触控键和移动端输入框。这些能力可复用。

当前实现的关键限制是：

- 终端对象、PTY、输出 chunk 都只保存在 Server 内存；Server 重启后无法恢复。
- 终端是工程级工具，不是可命名、可归档、可搜索的对话 Session。
- 输出只有原始 ANSI 流，没有结构化的命令/输入/输出历史，无法高效查看很久以前的内容。
- `close` 会直接杀 PTY；必须明确区分用户主动停止、页面离开、WebSocket 断开和服务重启。
- 没有 CLI profile、启动参数、权限模式和重启熔断模型。

因此不建议把新页面直接堆在当前 `TerminalPanel` 上；应复用其 xterm 和移动端 chrome，同时新增持久化终端会话层。PTY 仍由 Fastify Server 进程统一托管。

## 产品模型

### 1. Session 类型

在现有 Session 增加 `kind`：

```text
chat             现有 Codex 对话页，行为不变
terminal-chat    新的终端对话页
```

工程默认仍打开普通 `chat` 对话。用户从“新建终端对话”进入 `terminal-chat`，或在工程的最近会话列表中再次打开。建议路由为：

```text
/projects/:projectId/sessions/:sessionId       普通对话
/projects/:projectId/terminal/:terminalId      终端对话
```

也可以统一使用 Session 路由，只根据 `kind` 选择页面组件；不要让终端 Session 误进入现有 Codex turn 流程。

### 2. CLI Profile

Profile 是服务端维护的启动模板，而不是浏览器提交任意命令：

```json
{
  "id": "claude-code",
  "name": "Claude Code",
  "executable": "claude",
  "args": [],
  "env": { "TERM": "xterm-256color" },
  "permissionMode": "on-request",
  "restartPolicy": "manual"
}
```

首批内置 `codex`、`claude-code`、`shell` 三个 profile。`executable` 和 `args` 必须使用 argv 启动，不能把未经校验的字符串拼接后交给 shell；自定义 profile 只允许管理员在系统设置中配置。项目 cwd 必须来自已登记的工程路径。

### 3. 运行时组成

```text
Browser
  └─ terminal-chat React 页面 + xterm.js
       HTTPS / WSS
Server
  ├─ TerminalSessionService（鉴权、DB、历史、游标）
  └─ TerminalChatManager
       └─ node-pty -> codex / claude / shell
```

浏览器关闭页面、切换路由、WebSocket 断开或 iOS 进入后台时，Server 只移除订阅，不停止 PTY。Server 进程正常关闭时统一停止其托管的 PTY；再次启动后读取持久化状态，对 `desired_state='running'` 的终端重新启动 CLI。

## 持久化与恢复

### 数据库表

建议在 `packages/db` 增加以下表，迁移沿用当前 SQLite migration 风格：

```sql
terminal_sessions(
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  session_id TEXT UNIQUE REFERENCES sessions(id) ON DELETE CASCADE,
  profile_id TEXT NOT NULL,
  title TEXT NOT NULL,
  cwd TEXT NOT NULL,
  desired_state TEXT NOT NULL,       -- running | stopped
  state TEXT NOT NULL,               -- provisioning | running | detached | exited | failed | stopped | needs_attention
  restart_policy TEXT NOT NULL,      -- manual | on-unexpected-exit
  child_pid INTEGER,
  last_seq INTEGER NOT NULL DEFAULT 0,
  last_output_at INTEGER,
  last_exit_code INTEGER,
  last_signal INTEGER,
  restart_count INTEGER NOT NULL DEFAULT 0,
  restart_window_started_at INTEGER,
  next_restart_at INTEGER,
  last_error TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  stopped_at INTEGER
)

terminal_events(
  terminal_id TEXT NOT NULL REFERENCES terminal_sessions(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL,
  kind TEXT NOT NULL,                 -- output | input | resize | state | marker
  data TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY(terminal_id, seq)
)
```

`terminal_events` 只保存有界的热历史（例如每个 Session 20 MB 或 100,000 条事件）。完整长日志写入应用数据目录的 append-only 文件，按 Session 和日期分段、压缩和轮转；数据库保存文件段索引。这样 SQLite 不会被连续构建输出拖垮，也不会因为页面刷新丢失最近输出。

另外维护结构化 transcript（可由 `input`、行结束和运行状态 marker 异步生成），字段至少包括 `timestamp`、`stream`、`text`、`commandId`。它用于历史搜索和移动端回看，xterm 原始流仍是终端画面的事实来源。

### Server 重启恢复流程

1. Server 正常关闭时停止当前托管的 PTY，但保留 `desired_state`、profile、cwd、输出事件和重启策略。
2. Server 启动后扫描 `desired_state='running'` 的记录，并为每条记录重新创建 CLI 进程。
3. 新进程使用新的 PID 和 TTY；原 CLI 内部未持久化的交互现场不会保留。Codex/Claude 自身支持的 resume 能力可在后续通过 profile 参数接入。
4. 启动失败时记录 `failed` 和错误原因，不进行无限重试；由重启策略和熔断器控制后续动作。
5. 浏览器连接后发送 `terminal.subscribe(lastSeq)`。服务端先发当前元数据，再回放缺失 seq；游标不在热历史范围时返回日志下载/分页接口，而不是一次性塞进 WebSocket。

## 生命周期与防止反复杀死/重启

### 状态机

```text
provisioning -> running <-> detached
running -> exited -> (manual restart | backoff restart | needs_attention)
running -> stopped        （用户主动停止）
任何状态 -> failed        （不可恢复错误）
```

- `detached` 只表示当前没有浏览器订阅，进程仍然运行。
- WebSocket `close`、页面隐藏、路由切换、iOS Safari 挂起都只产生 detach。
- `stopped` 是用户明确点击“停止”，不能被自动重启。
- CLI 自己退出、被 OOM/信号杀死才算 unexpected exit。

### 推荐默认策略

- 新建终端对话默认 `restartPolicy=manual`，因为 Codex/Claude CLI 退出通常代表任务完成或需要用户处理。
- 用户可对单个 Session 开启 `on-unexpected-exit`；只在非零退出和异常信号时重启。
- 同一 Session 5 分钟内最多重启 3 次，退避 `1s/2s/5s/15s/30s`；达到上限进入 `needs_attention`，显示“已暂停自动重启”，必须手动恢复。
- 配置或 cwd 错误、可执行文件不存在、权限拒绝、用户主动 Ctrl-C 不自动重启。
- 每次重启前写入 marker 事件和原因，保留旧 pid/退出码；重启不是清屏，用户可以看到完整上下文。
- Server 启动恢复和 CLI 异常重启使用不同语义；Server 启动恢复不累计异常退出次数，避免服务部署造成熔断误判。
- 进程树使用 process group；停止时先发 `SIGINT`，短暂等待后 `SIGTERM`，最后才 `SIGKILL`。不能在客户端卸载组件时调用 stop。

前端也要有重连退避和单飞锁：同一 terminal 只允许一个连接尝试；页面重新可见时优先复用已有连接，不能同时创建多个 WebSocket 或重复发起启动请求。

## HTTP 与 WebSocket 协议

### HTTP

```text
GET  /api/projects/:id/terminal-sessions
POST /api/projects/:id/terminal-sessions
GET  /api/terminal-sessions/:id
PUT  /api/terminal-sessions/:id          重命名、desiredState、restartPolicy
POST /api/terminal-sessions/:id/restart  手动重启（带幂等 requestId）
POST /api/terminal-sessions/:id/stop     用户主动停止
GET  /api/terminal-sessions/:id/history?beforeSeq=...&limit=...
GET  /api/terminal-sessions/:id/transcript?q=...
```

创建接口只接受 `profileId`、工程内 cwd、标题、尺寸和策略；服务端解析 profile 并记录审计。`restart`、`stop` 必须幂等，重复点击不能产生多个子进程。

### WebSocket

建议新建 `/api/terminal-chat/ws`，不要改变现有 `/api/terminal/ws` 的消息兼容性。所有消息包含 `terminalId`、`connectionId` 和可选 `clientRequestId`：

```text
client -> terminal.subscribe { lastSeq, cols, rows }
server -> terminal.snapshot { state, seq, replay, output?, transcriptCursor? }
client -> terminal.input { data, mode: raw | line }
client -> terminal.resize { cols, rows }
client -> terminal.signal { signal: INT | TERM | HUP | KILL }
client -> terminal.detach
server -> terminal.output { seq, data }
server -> terminal.input-echo { seq, data }       （可选，用于审计/结构化历史）
server -> terminal.state { state, reason, pid, restartAt? }
server -> terminal.marker { seq, kind, text }
server -> terminal.error { code, message, retryable }
```

服务端对 input 做单连接顺序校验、大小限制和速率限制；断线期间前端最多缓存少量待发送输入，重连后需用户确认再发送，避免重复执行危险命令。输出采用 seq 去重，心跳/ack 只用于检测连接，不用于决定是否杀进程。

## 页面与交互设计

### 桌面端

终端对话页使用工作台主区域，不挤压现有聊天布局：

```text
工程/Session 标题     CLI profile  运行状态  ...
──────────────────────────────────────────────
可滚动 ANSI 终端画面（xterm.js，支持选择、搜索、复制、下载）
──────────────────────────────────────────────
一行运行摘要：连接、PID、运行时长、后台运行/自动重启状态
Profile / 模型(如适用) / 权限 / 重启策略 / 停止 / 重启 工具栏
输入框（默认逐行发送；可切换直通键盘模式）       发送
```

输入框默认是安全的 line mode：Enter 发送一行，Shift+Enter 插入换行，支持中文输入法；需要 `vim`、TUI 或 CLI 交互时切换 raw mode，输入框改为透明键盘捕获层。常用命令历史用上下箭头调用 shell/CLI 自己的历史，不在浏览器重复实现一份。

桌面快捷键：

- `Ctrl/Cmd+K` 聚焦输入框；`Ctrl+Shift+F` 搜索输出；`Ctrl+L` 发送清屏；`Esc` 取消当前搜索/关闭弹层。
- raw mode 下保留 `Ctrl+C/D/Z/L`、方向键、Tab、Home/End、Alt 组合键。
- 所有快捷键提供按钮等价物，避免依赖 hover 或记忆。

### iOS / 手机端

手机是远程查看、发送短命令和处理审批的轻量入口，不能假设 Safari 会永久保持 WebSocket：

- 页面使用 `100dvh`，底部工具栏计算 `env(safe-area-inset-bottom)`；监听 `visualViewport.resize`，键盘出现时只压缩终端容器，不滚动整个页面。
- body 禁止跟随终端滚动；终端 viewport 使用 `overflow: auto`、`overscroll-behavior: contain` 和 `-webkit-overflow-scrolling: touch`。向上查看历史时暂停自动跟随，显示“回到底部”按钮。
- xterm 保持有限 scrollback；更早内容通过“加载更早输出”分页追加，结构化 transcript 用虚拟列表，避免数万行 DOM。
- Session 历史放在可滑出的抽屉，条目显示 profile、最后输出时间、运行/退出/需处理状态；打开条目后恢复上次 scroll anchor，而不是跳到列表顶部。
- 底部保留三层结构：运行摘要、横向可滑动的工具/组合键行、输入框。组合键使用 `Ctrl`、`Alt`、`Shift` 锁存按钮，单击一次作用于下一键，双击锁定；方向键支持长按重复。
- 提供“输入”按钮打开真正的 iOS 文本输入框，设置 `inputMode=text`、`enterKeyHint=send`、关闭自动纠正和自动大写，并在 composition 期间不提交 Enter。粘贴走专用多行弹层，防止 iOS 剪贴板权限导致丢文本。
- Safari 进入后台时前端主动 detach WebSocket，但不发送 stop；回到前台后以 `lastSeq` 重新订阅。页面显示“后台运行中，已落盘 N 行输出”，而不是“进程断了”。
- 手机不强求后台通知；重新打开页面必须能从数据库/日志恢复状态。未来增加 Web Push 时只通知状态变化，不把实时输出推送到通知栏。

### 历史查看规则

历史分为两个入口：

1. Session 列表：按工程、profile、状态和最后活动时间筛选，支持归档/重命名。
2. 当前 Session 内：默认显示最新终端画面；向上滚动加载原始输出段或 transcript，保持 scroll anchor；搜索命中后定位到段落并可返回实时尾部。

不要把完整 ANSI 日志一次性放进 React state。前端维护 `lastSeq`、当前 viewport 和少量环形缓存，服务端按游标分页。

## 安全、资源和运维

- 所有 HTTP/WS 接口沿用现有登录 Cookie、CSRF/Origin 校验和项目权限；终端输出可能包含 Secret，日志下载和 transcript 搜索都要鉴权。
- profile、argv、环境变量由服务端控制；客户端只能选择已发布 profile，禁止传任意 shell、`CODEX_HOME` 或环境变量覆盖。
- 每个用户/工程限制并发终端数、单 Session 输出速率、热缓存大小和日志磁盘配额；超限进入 `needs_attention` 并保留原因。
- PTY 只能由 Server 内部管理器创建和控制，不暴露额外本地 IPC；记录创建、输入、信号、停止、自动重启和失败熔断审计事件。
- Server 停机钩子先完成状态和最后输出落盘，再停止托管的 PTY。`desired_state=running` 保持不变，以便下次启动重新创建 CLI。
- 运行中心显示每个 terminal-chat 的状态、PID、重启次数、最后输出和磁盘占用；支持批量停止，但批量操作必须二次确认。

## 分阶段实施

### Phase 1：终端对话 MVP

- 增加 `terminal-chat` Session、profile（`codex`/`claude-code`/`shell`）和页面路由。
- 把现有 `TerminalViewport` 抽成可复用组件，增加 line/raw 两种输入模式。
- 新增 terminal session API、持久化 metadata、事件 seq 和 transcript 分段。
- 浏览器断开、路由切换、iOS 后台只 detach；实现前台按 seq 恢复。

### Phase 2：Server 托管下的重启恢复

- 完善 Server 启动扫描、profile 恢复、状态 marker 和失败原因记录。
- 加入手动 stop/restart、unexpected-exit 策略、退避和熔断。
- 对支持恢复的 CLI 增加 profile 级 resume 参数，但不引入独立 supervisor。

### Phase 3：历史、运维和体验完善

- 压缩日志轮转、游标分页、transcript 全文搜索、下载和审计。
- 运行中心聚合、磁盘配额、profile 设置页、Playwright 移动端回归。
- 可选增加 Web Push 状态通知，不改变实时终端协议。

## 验收标准

- 关闭浏览器标签、切换工程、iOS Safari 进入后台，CLI 继续运行；重新打开后无重复输入，按 seq 补齐输出。
- Server 重启后，`desired_state=running` 的终端重新创建 CLI；历史输出仍可见，新旧运行边界有明确 marker，启动失败时不会无限创建进程。
- 用户主动停止后绝不自动重启；开启自动重启的 Session 在 5 分钟内超过 3 次异常退出后进入 `needs_attention`。
- Codex、Claude Code 和 shell 都能在独立 cwd 中启动；权限、profile、路径和 Secret 不由客户端任意覆盖。
- 桌面支持复制、粘贴、搜索、下载、raw 组合键和键盘快捷键；手机支持中文输入法、safe area、横向工具栏、终端局部滚动、历史分页和回到底部。
- 输出达到上限时有明确提示但页面不崩溃；长历史不造成整页卡顿，WebSocket 重连不创建重复 PTY。
- 为终端状态机、Server 启动恢复、重启熔断、seq 回放、幂等 stop/restart、中文 composition、iOS viewport 和桌面/手机端到端流程分别补充单元测试与 Playwright 测试。

## 最终建议

保持 PTY 由 Server 进程托管，不增加独立 supervisor。重点保证“网页关闭不影响进程”和“Server 重启后根据持久化状态重新启动 CLI”，同时明确后者不是接管原 PID。不要把 WebSocket 断线当作进程退出条件，也不要因为多次前端重连重复创建 PTY。这样 Codex、Claude Code 等命令可以共享同一套终端对话 UI，同时保持部署结构简单和现有普通对话页稳定。
